### What does .terraform.lock.hcl do?

The lock file records the exact provider version and checksums used by Terraform. It ensures reproducible deployments and prevents different team members from using different provider versions.

### Version Constraints

= 5.0.0
- Installs only version 5.0.0

>= 5.0
- Installs version 5.0 or higher, including future major versions

~> 5.0
- Installs any version from 5.0 up to but not including 6.0
- Allows updates while preventing breaking major-version upgrades

## What is an Implicit Dependency?

An implicit dependency occurs when one resource references an attribute of another resource.

Example:

```hcl id="vc6d9g"
resource "aws_subnet" "public" {
  vpc_id = aws_vpc.main.id
}
```

The subnet needs the VPC's ID, so Terraform automatically understands:

```text
VPC must exist before Subnet
```

You do not need to write:

```hcl id="c53w6g"
depends_on = [aws_vpc.main]
```

Terraform figures it out automatically.

# Question 1

## How does Terraform know to create the VPC before the subnet?

Terraform scans all resource references in the configuration.

In your subnet:

```hcl id="4zjlwm"
vpc_id = aws_vpc.main.id
```

Terraform sees:

```text
aws_subnet.public
        ↓
aws_vpc.main.id
```

This tells Terraform:

```text
Create aws_vpc.main first
Create aws_subnet.public second
```

Terraform builds a dependency graph from these references and uses that graph to determine creation order.

---

# Question 2

## What would happen if you tried to create the subnet before the VPC existed?

AWS would reject the request because a subnet must belong to an existing VPC.

A typical AWS error would be:

```text id="wvh6bh"
InvalidVpcID.NotFound
The vpc ID does not exist
```

Since Terraform detects the dependency automatically, it creates the VPC first and avoids this error.

**Document:** When would you use `depends_on` in real projects? Give two examples.

In real Terraform projects, you use `depends_on` only when **Terraform cannot infer the dependency automatically from resource references**, but  still need a strict creation order for correctness.

Here are two practical, real-world examples:

---

# 1. Forcing IAM permissions before workload startup (boot-time dependency)

Sometimes an EC2 instance (or container) doesn’t directly reference IAM resources in Terraform, but it **needs those permissions at startup** to function correctly.

### Example: EC2 must wait for IAM role attachment

```hcl
resource "aws_iam_role_policy_attachment" "app_attach" {
  role       = aws_iam_role.app_role.name
  policy_arn = aws_iam_policy.app_policy.arn
}

resource "aws_instance" "app" {
  ami           = data.aws_ami.amazon_linux.id
  instance_type = "t3.micro"

  depends_on = [aws_iam_role_policy_attachment.app_attach]
}
```

### Why this is needed:

* Terraform cannot always guarantee the IAM attachment is fully propagated before instance boot
* The application may fail at startup if it immediately tries to access AWS services (S3, Secrets Manager, etc.)
* `depends_on` ensures **IAM is fully ready before compute starts**

---

# 2. Ensuring network or security baseline exists before deployment

In some cases, resources are technically “independent” in Terraform, but operationally unsafe if created in the wrong order.

### Example: Ensure security group or firewall rules exist first

```hcl
resource "aws_security_group" "web_sg" {
  name   = "web-sg"
  vpc_id = aws_vpc.main.id

  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id
  instance_type = "t3.micro"

  vpc_security_group_ids = [aws_security_group.web_sg.id]

  depends_on = [aws_security_group.web_sg]
}
```

### Why this is needed:

* Normally Terraform already understands SG → EC2 dependency
* But `depends_on` is used when:

  * SG rules are managed separately (modules / remote state)
  * Or you want to guarantee **firewall rules exist before instance becomes reachable**
* Prevents a brief window where infrastructure is deployed but not secured

#  Key takeaway

Use `depends_on` only when:

- Dependency is **real in runtime**
- but not visible in Terraform references

**Document:** What are the three lifecycle arguments (`create_before_destroy`, `prevent_destroy`, `ignore_changes`) and when would you use each?

 Terraform lifecycle rules are basically **guardrails for how resources are replaced and updated**, especially when default behavior could cause downtime or accidental damage.

Here are the three key arguments and when to use each:

---

# 1. `create_before_destroy`

### What it does

Terraform creates the **new resource first**, then destroys the old one.

```hcl id="v7kq9a"
lifecycle {
  create_before_destroy = true
}
```

---

### Why it matters

Normally Terraform does:

❌ destroy → create (causes downtime)

With this:

✔ create → switch → destroy (zero/low downtime)

---

### When to use it

Use it when **replacing a resource must not cause downtime**, such as:

* EC2 instances behind a load balancer
* Auto Scaling group instances
* Production web servers
* Database read replicas (carefully)

---

### Real example

You change AMI:

* New EC2 is created first
* Then old EC2 is terminated

👉 prevents service interruption

---

# 2. `prevent_destroy`

### What it does

Prevents Terraform from destroying the resource completely.

```hcl id="g2m9xz"
lifecycle {
  prevent_destroy = true
}
```

---

### What happens if you try to destroy it

Terraform will fail:

```
Error: Instance cannot be destroyed
```

---

### When to use it

Use it for **critical, non-recoverable infrastructure**, such as:

* Production databases (RDS)
* S3 buckets with important data
* DNS zones (Route 53 hosted zones)
* Encryption keys (KMS keys)
* State storage buckets (Terraform backend)

---

### Real-world reason

This protects you from:

* accidental `terraform destroy`
* accidental module deletion
* destructive refactoring mistakes

---

# 3. `ignore_changes`

### What it does

Terraform ignores changes to specific attributes after creation.

```hcl id="d8q3lm"
lifecycle {
  ignore_changes = [tags, user_data]
}
```

---

### Why it matters

Normally Terraform tries to enforce **exact desired state**.

But sometimes external systems modify resources.

---

### When to use it

Use it when changes come from outside Terraform:

* Auto Scaling groups modifying instance metadata
* Kubernetes / config agents updating tags
* User data updated manually or by bootstrapping tools
* AWS services adding or modifying fields dynamically

---

### Real-world example

```hcl id="x0p9tt"
resource "aws_instance" "app" {
  ami           = data.aws_ami.amazon_linux.id
  instance_type = "t3.micro"

  lifecycle {
    ignore_changes = [ami]
  }
}
```

 Terraform won’t recreate instance if AMI changes in data source

---

#  Summary Table

| Argument                | Purpose                           | When to use                               |
| ----------------------- | --------------------------------- | ----------------------------------------- |
| `create_before_destroy` | Avoid downtime during replacement | Production compute, load-balanced systems |
| `prevent_destroy`       | Block accidental deletion         | Databases, S3 buckets, DNS zones          |
| `ignore_changes`        | Ignore external or unwanted drift | Tags, user_data, auto-managed fields      |

---

#  Important mindset 

Lifecycle rules are not “features to use everywhere”.

They are:

>  Safety overrides for edge cases where Terraform’s default behavior is too aggressive or too strict

#  5. Implicit vs Explicit Dependencies

##  Implicit Dependency (Automatic)

Terraform automatically creates dependency when one resource directly references another.

### Example:

```hcl
subnet_id = aws_subnet.public.id
```

👉 Terraform understands:

* EC2 depends on subnet automatically

✔ No need to write `depends_on`

---

##  Explicit Dependency (Manual)

Used when Terraform cannot detect dependency automatically.

### Example:

```hcl
depends_on = [aws_iam_role_policy_attachment.app_policy]
```

👉 Used when:

* No direct reference exists
* But order still matters

---

##  Key Difference

| Type     | How it works                    | Example      |
| -------- | ------------------------------- | ------------ |
| Implicit | Terraform detects automatically | subnet → EC2 |
| Explicit | You force ordering              | IAM → EC2    |
