## 1. What is Observability?

Observability is the ability to understand the internal state of a system by analyzing the data it generates, such as metrics, logs, and traces.

In modern distributed systems, failures can happen in many places. Observability helps engineers investigate and understand issues without having to predict every possible failure scenario beforehand.

### Monitoring vs Observability

| Monitoring                            | Observability                          |
| ------------------------------------- | -------------------------------------- |
| Tells you **when** something is wrong | Tells you **why** something is wrong   |
| Uses predefined alerts and thresholds | Allows investigation of unknown issues |
| Reactive                              | Exploratory                            |
| Focuses on known failure conditions   | Helps diagnose unexpected failures     |

### Example

Suppose your application suddenly becomes slow.

**Monitoring tells you:**

* CPU usage is 95%
* Error rate increased
* Response time crossed threshold

**Observability helps you discover:**

* Which service caused the slowdown
* Which request path is failing
* Whether the database or API dependency is responsible
* How the issue propagated through the system

In short:

> Monitoring detects problems.
> Observability explains problems.

## 2. The Three Pillars of Observability

### A. Metrics

Metrics are numerical measurements collected over time.

Examples:

* CPU usage
* Memory usage
* Disk utilization
* Request count
* Error rate
* Response latency

Common Tools:

* Prometheus
* Datadog
* Amazon CloudWatch

#### Example

```text
CPU Usage = 85%
Memory Usage = 3.2 GB
HTTP Requests = 1200/sec
```

Metrics are useful for:

* Alerting
* Dashboards
* Trend analysis
* Capacity planning

---

### B. Logs

Logs are timestamped records of events generated by applications and infrastructure.

Examples:

```text
2026-06-21 10:15:22 User login successful
2026-06-21 10:16:01 Database connection timeout
2026-06-21 10:16:05 Payment request failed
```

Common Tools:

* Loki
* ELK Stack (Elasticsearch, Logstash, Kibana)
* Fluentd

Logs are useful for:

* Root cause analysis
* Error investigation
* Security auditing
* Debugging applications

---

### C. Traces

Traces track the journey of a single request across multiple services.

In a microservices architecture, one request may travel through:

```text
Frontend
   ↓
API Gateway
   ↓
User Service
   ↓
Database
```

A trace records the time spent in each step.

Common Tools:

* OpenTelemetry
* Jaeger
* Zipkin

Traces are useful for:

* Finding bottlenecks
* Understanding service dependencies
* Debugging distributed systems

---

## 3. Why Do DevOps Engineers Need All Three?

Each pillar answers a different question.

### Scenario: Users report that payments are failing.

#### Metrics tell you WHAT is wrong

```text
Payment error rate increased from 1% to 25%
```

You now know there is a problem.

---

#### Logs tell you WHY it is wrong

```text
Database timeout after 30 seconds
```

You discover the cause.

---

#### Traces tell you WHERE it is wrong

```text
Payment Service
   ↓ 12 seconds
Database Query
```

You identify the exact component responsible.

---

### Combined View

| Pillar  | Question Answered   |
| ------- | ------------------- |
| Metrics | What is broken?     |
| Logs    | Why is it broken?   |
| Traces  | Where is it broken? |

Without all three, troubleshooting becomes significantly harder.

### Task 2: Set Up Prometheus with Docker
Create a project directory for this entire observability block -- you will keep adding to it over the next 5 days.

```bash
mkdir observability-stack && cd observability-stack
```

Create a `prometheus.yml` configuration file:
```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

scrape_configs:
  - job_name: "prometheus"
    static_configs:
      - targets: ["localhost:9090"]
```

This tells Prometheus to scrape its own metrics every 15 seconds.

Create a `docker-compose.yml` to run Prometheus:
```yaml
services:
  prometheus:
    image: prom/prometheus:latest
    container_name: prometheus
    ports:
      - "9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
      - prometheus_data:/prometheus
    command:
      - '--config.file=/etc/prometheus/prometheus.yml'
    restart: unless-stopped

volumes:
  prometheus_data:
```

Start Prometheus:
```bash
docker compose up -d

### Task 3: Understand Prometheus Concepts
Explore the Prometheus UI and understand these concepts:

1. **Scrape targets** -- endpoints that Prometheus pulls metrics from at regular intervals (pull-based model)
2. **Metrics types:**
   - `Counter` -- only goes up (total requests served, total errors)
   - `Gauge` -- goes up and down (current CPU usage, memory in use, active connections)
   - `Histogram` -- distribution of values in buckets (request duration: how many took <100ms, <500ms, <1s)
   - `Summary` -- similar to histogram but calculates percentiles on the client side
3. **Labels** -- key-value pairs that add dimensions to metrics (e.g., `http_requests_total{method="GET", status="200"}`)
4. **Time series** -- a unique combination of metric name + labels

### Task 4: Learn PromQL Basics

```

**Document:** What happens when retention is exceeded? Why is a volume mount important for Prometheus data?

**Retention exceeded**
- Prometheus automatically removes the oldest TSDB data blocks when the configured retention period or retention size is exceeded. This prevents unlimited disk growth.

# Counter vs Gauge

## Counter

A counter only increases over time.

Characteristics:

* Monotonically increasing
* Resets only when the application restarts

Example:

```text
http_requests_total
```

Each incoming request increases the value.

Real-world example:

* Total number of API requests served.

---

## Gauge

A gauge can increase or decrease.

Characteristics:

* Represents current state
* Can move in either direction

Example:

```text
process_resident_memory_bytes
```

Memory usage changes continuously.

Real-world example:

* Current CPU utilization.
* Current active database connections.

# Data Retention and Storage

Prometheus stores metrics inside its local TSDB (Time Series Database).

Current storage path:

```text
/prometheus
```

Retention configuration:

```yaml
--storage.tsdb.retention.time=30d
--storage.tsdb.retention.size=1GB
```

### What happens when retention is exceeded?

Prometheus automatically deletes the oldest data blocks when either:

* Data age exceeds the configured retention time.
* Database size exceeds the configured retention size.

This prevents unlimited disk growth.

### Why is a volume mount important?

```yaml
- prometheus_data:/prometheus
```

The volume preserves TSDB data across container restarts.

Without the volume:

* Historical metrics are lost when the container is recreated.

With the volume:

* Metrics remain available even after restarting Prometheus.

# Key Learnings

* Prometheus uses a pull-based monitoring model.
* Metrics are collected through scrape targets.
* PromQL enables querying and aggregation of metrics.
* Counters track cumulative values while gauges represent current state.
* Retention policies control TSDB growth.
* Persistent volumes are essential for preserving monitoring data.
